#### AX-01: Builder Code Fee Rebate — **IN-SCOPE-NEW**

**Mechanism:** Any HL account can register as a "builder" and embed a builder code in
all order API calls. The builder earns up to 50% of taker fees generated by those orders.
This is a self-rebate: K280's bot wallet registers itself as builder, routes own orders
with own builder tag, receives 50% of taker fees back.

**Numbers:**
- Base taker fee: 0.045% (Tier 0)
- With builder self-rebate: effective ~0.022%
- K280 turnover: estimated 2-4 full portfolio rotations/month
- At $1M AUM, 3x/month turnover: $3M notional/month × 0.023pp savings = $690/month → $8,280/year
- At $10M AUM: $82,800/year saved — material Sharpe improvement

**Why not already done:** K280 was built before K355 documented the builder code program.
The K355 report mentioned "builders earn 40% of fees" (a rough figure — actual cap is 50%
per fee docs). No prior wave implemented this.

**Why not closed-line:** Not a regime filter, ML allocator, cross-venue arb, or stablecoin yield.
Pure friction reduction via protocol-level optimization.

**HL exposure impact:** NONE (existing K280 capital — no new allocation).

**K266 gate feasibility:** FEASIBLE. Implementation is API-level config change, not a new strategy.
No Sharpe gate needed — it reduces costs, cannot make K280 worse.

**Effort:** 1 wave (K369). Steps:
1. POST `/exchange` with `{type: "builderSetup", builderAddress, name, feeRate: 0.0005}`
2. Modify K280 order submission to include `builderAddress` field
3. Verify builder rebate appears in HL account statements
4. Compute net Sharpe improvement over 30-day forward test

#### AX-09: Liquidation Cascade Fade Signal — **IN-SCOPE-NEW**

**Mechanism:** HL is fully on-chain — all liquidations are published to the L1 in real-time.
HL WebSocket and REST API expose liquidation events with notional size, asset, direction.
Strategy: Subscribe to HL liquidation feed → detect large cumulative forced closes in
5-minute window above threshold → fade the cascade direction (mean-reversion post forced selling).

**Why this is novel:**
1. CEXs do not expose liquidation data in real-time (opacity is structural). HL does.
2. K280 is a carry strategy — orthogonal direction. No overlap.
3. K297' (OrderFlow Phase 38) uses OI/funding signal for RWA perps, not liquidation cascade.
4. kkdemian highlights "on-chain liquidation transparency" as HL's unique edge — this
   is a direct operationalization of that edge.

**Signal logic (preliminary):**
- Subscribe: `wss://api.hyperliquid.xyz/ws` → `{type: "liquidations"}`
- Aggregate: sum notional of forced closes per 5-min window per asset
- Threshold: > $5M aggregate liquidated notional in 5-min
- Signal: FADE direction of cascade (if mass long liquidation → go long; mass short → go short)
- Hold: 15-30 min (wait for forced selling to clear)
- Exit: hard stop if notional > 2× entry bar

**Why this might work:** Liquidation cascades create temporary price dislocations
(forced sellers/buyers exit without regard for fair value). Post-cascade, prices
revert as the forced flow exhausts. This is well-documented in CEX research but
hard to exploit there (private data). HL's on-chain transparency makes it tractable.

**HL exposure impact:** ADDS. Must size-cap at ≤5% portfolio (→ total HL ≤62.5%, within cap).

**K266 gate:** FEASIBLE (if backtest passes Sharpe >1.5, permutation p<0.05, OOS purity).
This is a new strategy — full K266 gates must be run.

**Effort:** Multi-wave. K370 = signal research + backtest. K372+ = forward test + live.
